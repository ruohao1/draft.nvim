# v0.1.0-beta.1 — Linux/OpenCode candidate

**Status: prepared locally; not tagged or published.** The proposed version is
`v0.1.0-beta.1`. The exact tested checkpoint, local results and remaining release
gates are in the [release validation record](../validation/2026-10-04-linux-beta-release.md).
Do not configure a plugin manager to fetch this tag until it exists.

The published baseline remains
[v0.1.0-alpha.1](https://github.com/ruohao1/draft.nvim/releases/tag/v0.1.0-alpha.1)
at `514d9460cf09e970ba325c29fd7aadc5e2e15ba3`. Its hosted CI does not validate this
candidate. Use the [installation and version-change guide](install-upgrade-rollback.md).

## What the candidate adds

- OpenCode chat beside the source, with selected saved files and explicit Send.
  Opening, model selection and hiding/reopening do not submit work.
- Automatic frozen review when a proposal is ready. Typing keeps composer focus
  until Escape. File approval advances; rejection stays visible. Batch approval
  requires visiting every pending diff.
- Follow-up discussion and revisions while review is pending, with fresh review
  for replacement proposals. Accepted files remain saved.
- Next-turn model selection, visible startup stages, safe Retry when confirmed
  by the controller, and clearer Cancel/Close recovery with drafts preserved.
- A floating native-review picker with search and recent entries first, plus
  native terminal resize/recovery improvements. Native review remains after-write.
- Repeatable Linux acceptance, terminal-key coverage and installation checks
  proving core chat works without tmux.

Chat and standalone staging edit isolated copies. Project files change only
after explicit approval of the frozen proposal. The diff appears after
generation finishes; this is not a live per-tool approval stream.

The optional native CLI companion is a separate workflow. It writes directly
after its permission flow, and `:NvimAIReview` inspects those existing writes.
Use `:NvimAIChatReview` for chat proposals.

## Supported and tested stack

| Component | Candidate scope |
| --- | --- |
| OS | Linux; local evidence on x86_64. macOS and Windows launches are disabled. |
| Neovim | 0.12+ with LuaJIT; tested and CI-pinned at 0.12.4. |
| OpenCode | Exactly 1.18.34 / ACP 1 for managed OpenCode and staging. Other versions are refused. |
| Python | Python 3, standard library only; local 3.14.4, Ubuntu CI uses system Python 3. |
| Isolation | Working Bubblewrap and user/PID namespaces; local Bubblewrap 0.11.1. |
| Utilities | Git, POSIX shell and ripgrep; local Git 2.53.0 and ripgrep 15.2.0. |
| tmux | Optional for core chat. Full integration recommends 3.7+; local acceptance and the CI configuration use 3.7c. |

CLI installation and account authentication are separate. Setup reads no
credentials and sends no prompt. Installed OpenCode tests use a scripted local
provider; live-account acceptance on 1.18.34 remains a separate release gate.
Codex and Claude native adapters remain available, but this candidate does not
claim new live-provider acceptance for them.

## Known limits

- Chat scope is fixed until confirmed Close/New. Selected files must already
  exist, be saved text files, and have permissions `0644` or `0755`.
- Chat does not create, delete or rename files, or change their modes.
- Multi-file approval is not atomic. Accepted files stay saved if a later file
  conflicts, fails or is rejected.
- A new conversation starts fresh context. There is no automatic crash recovery
  or transcript restoration. Retained interruption artifacts are not resumable
  approval authority.
- A disconnected controller may leave cleanup or publication uncertain. Follow
  the displayed recovery instructions, preserve unsaved work, and inspect
  uncertain files before restarting. Close does not revert accepted changes.
- Secondary diff-footer hints can truncate at 70 columns; file and batch actions
  remain available. Wider windows expose more hints.

See the [acceptance checklist](../validation/linux-beta-checklist.md) for the
expected discussion, model, review and recovery journey. Before publication,
complete candidate hosted CI, user acceptance and the explicitly authorized
current-version provider check described there. Tags, publication and provider
requests require their own authorization.
