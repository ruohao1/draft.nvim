# Manual proposal corrections design

Recommend a separate editable correction draft for one pending file in a Draft conversation. An explicit Freeze action creates a fresh immutable proposal revision through the existing revision registry. The user then reviews and approves those frozen bytes through the existing guarded publisher. Editing and freezing never publish project files or invoke a model.

This is a design recommendation for [ISQ-461](<https://linear.app/isqrd/issue/ISQ-461/design-manual-proposal-corrections-as-fresh-frozen-revisions>), investigated on 2026-10-17 against Draft main at `90432f510cd1ddeb8321004a986f140fe2d3da37`. Implementation has not started. The final acceptance condition—assessment against actual daily-use friction—is still open: a concrete example was requested, but none has been supplied. The example below is illustrative, not user evidence. This extends the [claudecode.nvim study](<https://linear.app/isqrd/document/claudecodenvim-study-architecture-diff-review-and-lessons-for-draft-7658617adef7>) and the completed <issue id="41fdac01-8115-44e1-b6fd-6dc43bf06e03" href="https://linear.app/isqrd/issue/ISQ-460/check-review-byte-fidelity-and-publication-outcomes-against-existing">ISQ-460</issue> byte-fidelity audit.

The useful upstream lesson is that small corrections can happen where a proposal is reviewed. Draft should preserve its own immutable approval boundary when adopting that interaction. The existing revision path already snapshots pending proposal bytes, preserves decided-file context, validates sources, retires old authority, and installs a fresh identity. It is the right place to add manual corrections. Its current integration assumes a model turn, so exposing it as a new command is more than making a buffer writable. [Registry and revision handoff](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-conversation-review.py#L117-L181>), [model-dependent replacement admission](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/lua/ai/conversation.lua#L528-L591>).

| Approach | Result and cost | Recommendation |
| -- | -- | -- |
| Keep using a model follow-up | No new state or UI. Every correction still requires describing the change and another provider turn. | Keep as the current workflow; defer this feature if actual friction does not justify it. |
| Separate editable draft, explicit freeze, ordinary approval | Reuses frozen snapshots, durable retirement and the guarded publisher. Adds a local editing state and a non-model correction transaction. | Preferred design if the benefit is validated. |
| Make the frozen pane writable or save its contents directly | Breaks the correspondence between reviewed bytes, proposal identity and publication evidence. Requires a different approval contract. | Reject for Draft. |

The first version is limited to an existing conversational review, one pending file at a time, and the conversation's fixed selected paths. Accepted, rejected and unchanged files cannot become correction targets. No new files, renames, mode changes, standalone staged-review integration, multi-buffer drafts, persistent draft recovery, unified diff mode, provider support or new configuration are included.

The proposed interaction is deliberately explicit. These command names describe the proposed interface; they do not exist yet.

1. Show a pending file using the existing review navigation. Run `:NvimAIChatEditProposal` or choose “Edit proposal” in the existing actions menu. Validate the current owner, review identity, source buffers and frozen handle. Copy that file's exact proposed bytes into a separate scratch buffer. Keep both original frozen panes immutable.
2. Label the scratch buffer “Editable correction — not published”, show the target path, and show whether it represents zero bytes or has a final newline. Use ordinary Neovim editing behavior, including undo. Do not install the review pane's single-letter approval/rejection mappings in this buffer.
3. While a correction exists, the semantic owner blocks approval, rejection, model follow-up and another correction through every command, menu and old callback. This must be an owner state check, not just disabled buttons. Starting editing advances the view revision so an already-open confirmation cannot act afterward. Keep controller-disconnection reporting active.
4. Run `:NvimAIChatFreezeProposal`. Validate and snapshot the draft, preflight its encoded command size, and recheck source/frozen guards. During the bounded handoff, make the submitted draft temporarily nonmodifiable. Freezing is the only transition from editable text to a replacement proposal; buffer writes, hiding and window closure do not trigger it.
5. After positive retirement and replacement evidence, adopt the new frozen review. Use the existing first-pending-file presentation policy; if presentation is deferred, the user reopens it normally. Show that this revision contains a manual correction. Approval still requires the ordinary explicit action and its existing guards.
6. `:NvimAIChatDiscardCorrection` discards only the local draft, with a modified-buffer confirmation when needed. Resume the original review only if its owner, identity and guards are still eligible. Reinvoking Edit while a draft is hidden focuses that draft.

For example, a pending `main.lua` proposal contains `local timout_ms = 1000\n`, and another selected file has already been accepted. Edit the proposed identifier to `timeout_ms`, freeze, inspect the replacement, then approve. The accepted file and its receipt remain intact; the old pending proposal can no longer be approved. This saves a model follow-up only if editing and refreezing is actually easier for the user.

The owner needs explicit states for a pending review, editing a correction, freezing a correction and recovery. Normal success returns to a pending review with a fresh identity, or settles the round if no changes remain. These transitions are separate from model generation.

| Transition or result | Authority and user-visible behavior |
| -- | -- |
| Begin editing | No proposal is mutated or retired. Keep a local correction identity bound to owner, round, revision, token, receipt sequence and target path. Hold no filesystem proposal lock for the duration of typing. |
| Local validation or size refusal | Keep the editable draft and the existing review identity. Do not send a command, consume a serial, retire authority or fault the controller. |
| Explicit freeze | Send one new correction operation. Its fresh command serial/callback lease and complete predecessor identity reject duplicates and late replies. No model turn or worker generation is fabricated. |
| Exact same bytes as the pending seed | Dispose of any unused candidate and positively revalidate the predecessor. Keep its token/revision. Do not create a history entry or consume a manual-revision budget. Old confirmation callbacks stay invalid. |
| Changed bytes and successful handoff | Retire the old pending authority before exposing the fresh token. Increment proposal revision within the same round and reset the new receipt sequence. |
| Corrected target equals its saved baseline | Its new state is unchanged, not accepted or rejected. Other pending proposals remain pending; settle if none remain. Earlier decisions remain truthful. |
| Recoverable pre-retirement refusal | Return to editing only after candidate cleanup and predecessor eligibility are proven, including editor checks. Preserve the draft. |
| Retirement started, cleanup unproven, lost reply or guard failure | Enter recovery; enable no approval based on either proposal. Preserve draft text and confirmed writer outcomes. Never infer restoration from a timeout or remove a retirement marker. |

The internal operation should be a new `correct` command, with the existing immutable conversation envelope and predecessor review identity, exact decision context, captured source hashes for the full selection, one selected pending `path`, and the full UTF-8 `replacement` string. The controller derives manifest paths and tokens from its registry; the UI does not supply arbitrary manifest paths or a replacement token. Closed-field validation applies on both sides.

Use a distinct `corrected` result, rather than fabricated model `submitted`/`settled` events. Its variants distinguish a reviewable replacement with retired-predecessor evidence, unchanged/refused operations with active-predecessor plus candidate-retirement evidence, and failures that require recovery. Only the trusted Neovim adapter can mark editor context valid after checking source buffers, aliases and frozen panels. The driver must recognize the new terminal result and clear its deadline.

Keep `turn_id`, `worker_generation` and the proposal's real model-generation reference unchanged for a manual correction. The fresh command serial, token and proposal revision provide operation and approval identity. Record manual provenance in review history and display; do not relabel the bytes as generated by the last model or add a fake transcript turn. A later real follow-up must start from the corrected pending seeds and include truthful decision context and a bounded manual-correction note. Do not replay a provider prompt merely to update its history. [Existing protocol bindings](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-conversation-protocol.py#L128-L225>), [current follow-up prompt context](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-conversation-turn.py#L211-L219>).

The transaction should reuse the existing trusted components in this order:

1. Acquire the predecessor through `ReviewRegistry.begin_revision`. Verify exact decision context and live selected-file identities/content. Obtain frozen pending seeds and context-only decided files under `PendingReview` ownership.
2. Compare the submitted target bytes with its frozen seed before checking capacity for a changed revision. A no-op can return active-predecessor evidence after revalidation without allocating a candidate. Otherwise, create a private workspace with `prepare_workspace`. Replace only the target seed. Retain all other pending proposed bytes; retain the current saved baselines for decided files. The controller owns the workspace/candidate immediately upon allocation, including every cleanup and EOF path.
3. Freeze through `freeze_workspace(..., multi=True, force_review=True)`, then use the existing seed comparison and retirement/install logic. Revalidate disk identities/content before the handoff. This path must not construct a `Turn`, launch ACP, or call the project publisher.
4. `PendingReview.retire` verifies the candidate, writes its origin, and fences the predecessor before registry installation. An attempted or torn fence is sufficient to forbid restoration. No later exception makes the old token safe again.
5. Before UI adoption, the adapter rechecks the captured source buffers/aliases and immutable frozen handle, validates the returned frozen reference, and requires semantic acceptance for the current correction operation. A source-buffer edit while the controller was working can therefore force recovery even after durable retirement.
6. Later approval uses the existing publisher and receipt normalization. Freeze evidence is never a write receipt.

The freezer already supports private workspaces without a provider, and `PendingReview` already supplies the durable handoff. Extend the registry/controller's ownership of an unfinished manual candidate so close/EOF can retire or retain it safely if installation fails or its reply is lost. Merely calling `finish_revision` without candidate ownership would leave a cleanup gap. [Workspace/freezer](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-staged.py#L393-L446>), [retirement ordering](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-staged-decisions.py#L297-L388>), [adapter admission](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/lua/ai/conversation_controller.lua#L253-L338>).

Cancellation is ordered against the handoff, not inferred from how quickly the UI responds. If cancel/close is handled before retirement, clean up the candidate and retire the current review as requested. If retirement has started or already finished, retire the owned replacement as well; never reactivate the predecessor. A bounded synchronous correction may finish before an already-sent cancellation is processed. Its late result cannot reopen the UI because the cancellation has a newer callback lease. Do not claim cleanup succeeded until there is positive evidence.

Hiding a window retains the correction buffer. Cancel/close retires proposal authority but preserves modified correction text as an editable detached scratch buffer, with Freeze disabled. Explicitly discarding that text is a separate user action. Loss of a correction buffer never means approval. Forced buffer deletion or editor death can lose unsaved scratch text; this design offers no crash recovery. On controller loss, preserve text that remains in Neovim, enter recovery, and never automatically replay a freeze or adopt private proposal artifacts. Already published files and their receipts survive all these paths.

A replacement preserves prior accepted/rejected/unchanged decisions as context; it does not rerun them or roll back accepted files. The new writer journal represents those files as unchanged while the registry carries their earlier outcomes forward. Reset visitation for every still-pending file, including those whose proposed bytes did not change, because the new token represents a new review. Opening the correction draft does not count as reviewing the frozen replacement. Per-file approval requires a real current frozen view; batch approval requires every remaining pending file to be visited under the new identity. Decided context is excluded from that requirement. [Inherited outcomes](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-conversation-review.py#L29-L99>), [shared review guards](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/lua/ai/staged_review.lua#L606-L689>).

Exact-byte handling needs explicit metadata because Neovim displays a zero-byte file and a single newline as one empty line. Initialize draft lines by removing exactly one terminal newline from the frozen bytes before splitting; initialize `endofline` from those bytes. Encode by joining lines with LF and appending exactly one LF only when `endofline` is true. Preserve all trailing blank lines. Set `fixendofline=false`, UTF-8/unix metadata, no swap/undo persistence and no modelines; do not silently normalize text at Freeze.

| Intended bytes | Draft lines | Final-newline flag |
| -- | -- | -- |
| zero bytes | one empty line | off |
| `\n` | one empty line | on |
| `x\n` | `x` | on |
| `x\n\n` | `x`, empty line | on |
| `\n\n` | two empty lines | on |

The UI must visibly distinguish the first two cases and explain `:setlocal endofline` / `:setlocal noendofline`. Deleting all visible text while the flag remains on produces one newline; zero bytes requires turning it off. Reject invalid UTF-8, BOM, CR, NUL or embedded line separators inside a returned line, and reject nonempty text without a final newline. Revalidate relevant buffer options, byte content and changedtick at Freeze. If text or metadata changes unexpectedly after the submission snapshot, never silently discard those newer edits or treat them as the frozen candidate. The existing publisher remains responsible for exact saved bytes. [Supported staged-text contract](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-staged.py#L69-L78>), [ISQ-460 validation](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/docs/validation/2026-10-16-review-byte-fidelity.md>).

Keep the current limits: 16 selected existing files, 1 MiB aggregate proposal bytes, 20,000 newline characters per file, and a 1 MiB encoded controller command. Preflight the exact JSON envelope before dispatch, rather than discovering oversize inside the driver's fault path. JSON escaping and envelope overhead mean some otherwise supported large files will not fit a correction command. Refuse those corrections without truncation and retain the draft; do not increase limits or add file-path/streaming transport in this version. Recheck the decoded limits and aggregate bytes in Python.

Manual corrections must not create unbounded history outside the existing 64-model-turn limit. Recommend an additional internal cap of 64 changed manual revisions per conversation, checked by both owner and controller before allocating a replacement. No-op/discard operations do not consume it; cancel, close and approval of the current proposal remain available at the cap. Keep status/history output within existing display/event budgets and store only identity/decision/provenance metadata in history, not repeated full draft contents. This is an implementation requirement, not a claim that the cap exists today. [Transport limits](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/scripts/nvim-ai-conversation-protocol.py#L10-L15>), [driver admission](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/lua/ai/conversation_driver.lua#L438-L473>), [current model-turn limit](<https://github.com/ruohao1/draft.nvim/blob/90432f510cd1ddeb8321004a986f140fe2d3da37/lua/ai/conversation.lua#L1047-L1054>).

The implementation boundary reaches the following existing owners. No separate publisher, generic revision framework, new dependency or public setup option is needed.

| Area | Required reach |
| -- | -- |
| `lua/ai/init.lua`, `chat.lua`, `chat_view.lua` | Command registration/runtime forwarding, existing action menu, draft lifetime/focus, truthful status, cancel/close text and confirmations. |
| `lua/ai/conversation.lua` | Correction states/identity, all decision gates, result validation, bounded manual history and provenance. Factor only the replacement checks actually shared with model follow-ups. |
| `lua/ai/conversation_controller.lua` | Capture/revalidate sources, preserve frozen guards, inspect/adopt replacement, retain draft on refusal or stale completion. |
| `lua/ai/conversation_driver.lua` | Safe size preflight and new terminal-result recognition. Preserve serial/deadline/disconnection guarantees. |
| `lua/ai/staged_review.lua` | Reuse immutable panels and visitation/approval guards; expose only the narrow read-only target data needed by the chat correction UI. |
| `scripts/nvim-ai-conversation-protocol.py`, `nvim-ai-conversation.py`, `nvim-ai-conversation-review.py` | Strict correction command, non-model dispatch, candidate ownership/cleanup, budget enforcement, fresh revision and result evidence. |
| `scripts/nvim-ai-staged.py`, `nvim-ai-staged-decisions.py` | Reuse freezer and durable handoff; change only if implementation exposes a concrete shared-contract gap. |
| `scripts/nvim-ai-conversation-turn.py` | Truthful context for the next real follow-up after manual correction; no provider call during correction itself. |
| Tests/fixtures and usage docs | Extend real controller fixtures and public-action coverage; update both `README.md` and `doc/draft.txt`; capture the changed review/draft UI for the implementation PR. |

Regression coverage should exercise authority and bytes at the real boundaries, with small semantic/UI tests where the behavior is editor-owned.

| Required case | Evidence to assert |
| -- | -- |
| Change one pending file | No provider invocation or project write at Edit/Freeze; fresh token, revision +1, retired old token; approval publishes exactly the frozen correction. |
| Mixed accepted/rejected/pending files | Prior receipts and accepted bytes survive; decided files cannot be edited; untouched pending seeds remain exact; subsequent real follow-up sees truthful context. |
| No-op and return to baseline | No-op keeps token/history budget; baseline reversion becomes unchanged; round settles correctly if no pending files remain. |
| Byte round trips | Zero bytes, one newline, multiple blank lines, trailing blank lines, Unicode and undo/redo preserve intended bytes through draft → freeze → reopen → publication. Unsupported text/options are refused without normalization. |
| Stale UI/operation | Old confirmations, navigation snapshots, repeated Freeze, wrong path/token/receipt/serial, callbacks after cancel/close, and edits after submitted changedtick cannot act on a different revision. |
| Source and frozen drift | Dirty loaded aliases, identity replacement, same-path disk changes, changed decided-file context, frozen-panel changes/deletion and metadata changes refuse safely. |
| Visitation | Fresh identity clears all pending visits; draft viewing is not a visit; batch approval fails until all remaining frozen files are visited. |
| Failure before/after retirement | Inject candidate creation, freeze, cleanup, origin/followup write, torn-fence, install and reply failures. Restore only with positive pre-fence proof; no old approval after retirement starts. |
| Lifecycle interruption | Hide/reopen retains text; discard affects only draft; cancel/close retires the right owned candidates and preserves modified text; EOF/controller loss requires recovery; duplicate commands cannot replay effects. |
| Bounds | Actual encoded 1 MiB boundary including escape-heavy text and envelope overhead; aggregate/line limits; 64 changed manual revisions; no-op and cleanup still work at the cap. |

These passes support reuse of the current machinery; they do not test the proposed feature. A separate clean headless Neovim probe round-tripped zero bytes, one newline, `x\n`, `x\n\n` and `\n\n` using lines plus `endofline`. It also confirmed that deleting every visible line leaves `endofline=true` when it was already enabled. No production files were changed.

Before selecting implementation, compare this interaction with an actual correction from daily use: what the model proposed, the intended correction, and why a follow-up or current review workflow was cumbersome. Repeated small edits confined to one pending file would support this design. Predominantly cross-file changes or rare corrections would favor staying with model follow-ups. Until that evidence arrives, keep <issue id="596c6f39-43df-4716-bd63-3ace74efa811" href="https://linear.app/isqrd/issue/ISQ-461/design-manual-proposal-corrections-as-fresh-frozen-revisions">ISQ-461</issue> in review with the benefit-validation acceptance item open. If implementation is selected, keep its plan on the feature branch and include it with the implementation PR; create no standalone plan PR.

Not checked: real daily-use benefit, a running correction UI, or live-provider behavior. The material implementation risk is a failed ownership handoff losing track of an approvable candidate; the other deliberate limits are in-memory draft recovery and large corrections that exceed the existing encoded-command budget.
